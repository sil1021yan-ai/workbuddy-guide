# 第 24 章 如何进行多 Agent 系统设计

> 内容来源：WorkBuddy 官方指南与社区实战案例整理（非官方，© 本指南作者，保留所有权利）

<Paywall part="3" variant="banner" />

一个对话用久了，你会撞上三堵墙：**上下文太长它开始忘事、角色太多它开始串味、
活太多它只能排队干**。这三堵墙，就是多 Agent 系统存在的理由。

这一章用人话讲清多 Agent 的原理，并带你搭一条真实的内容生产流水线。
学完你就明白：所谓多 Agent，不是玄学，就是**给 AI 团队定编制、定岗位、定交接单**。

## 一、先想清楚：你需要多 Agent 吗

| 信号 | 说明 | 解法 |
|-|-|-|
| 对话越长越忘事 | 上下文被塞满，早期要求被稀释 | 把独立任务拆给子 Agent（干净的上下文） |
| 一会儿当写手一会儿当审稿 | 角色混杂，输出风格摇摆 | 一个角色一个 Agent，各司其职 |
| 几件互不依赖的活要干 | 单线排队浪费时间 | 并行派发，同时开工 |
| 需要不同"专业工具" | 主对话工具太杂容易用错 | 子 Agent 只配它需要的工具 |

**反向信号**：任务 10 分钟就能干完、或者步骤之间强依赖你逐步拍板——别拆，
单对话更省事。多 Agent 是组织成本，不是免费午餐。

## 二、三个核心概念（人话版）

| 概念 | 类比 | 关键特性 |
|-|-|-|
| 主对话 | 项目经理 | 只有它一直"记得"全局；负责拆活、派活、验收 |
| 子 Agent（subagent） | 外包专才 | 干完就解散；**看不到你和主对话的聊天记录**，只看到你派活时写的任务书 |
| 专家包（Expert） | 挂名顾问 | 带着成熟方法论上岗，适合单点请教；不能和子 Agent 混用 |

> **最重要的一个事实**：子 Agent 是"新人入职"。它不知道你之前的任何对话——
> 你以为写了背景，其实它根本看不见。所以派活的任务书必须**自包含**：
> 目标、材料路径、格式要求、验收标准，一样不能少。

## 三、三种经典架构

### 架构 1｜串行流水线（上游 → 下游）

适合：内容生产、翻译 + 润色、报告生成这类**顺序依赖**的活。

```
选题 Agent → 写作 Agent → 审稿 Agent → 排版 Agent
   （每道工序产出一个文件，下一道只读上游的文件开工）
```

要点：**交接靠文件，不靠记忆**。每道工序把产物写到磁盘，下一道从磁盘读。

### 架构 2｜并行地图归并（分头查 → 汇总）

适合：调研、竞品对比、多方案探索这类**互不依赖**的活。

```
主对话 ──┬─→ 调研 Agent A（渠道一）──┐
         ├─→ 调研 Agent B（渠道二）──┼─→ 主对话汇总成对比报告
         └─→ 调研 Agent C（渠道三）──┘
```

要点：三个任务书**格式统一**（同样的输出模板），汇总才不痛苦。

### 架构 3｜主从协作（派活 + 验收循环）

适合：长期项目，主对话当 PM，子 Agent 当执行层。

要点：主对话负责**拆活、派活、验收、记账**（用共享任务清单跟踪状态），
不亲自干活；子 Agent 交付后由主对话检查，不合格打回重做。
